① Model benchmark

Four model families × two scenarios (pre-departure A and inflight B) on identical splits. XGB wins both

🛠 How the four models are trained

Same rows, same splits, same labels. Only the model class changes — each family is trained twice, once per scenario, on the identical date-based train / val / test partition.

TRAIN 11.07 M rows · Jan 1 → Apr 30 · 4 months
VAL   2.82 M rows · May 1 → May 31 · 1 month
TEST 2.71 M rows · Jun 1 → Jun 30 · 1 month

Split is by calendar date, not random — a single train service runs across many stops on one day, so a random row split would leak future answers into the past. Day-granularity guarantees a service ID never straddles a partition.

For every (model, scenario) pair the same loop runs: fit scaler on train rows only → train with early stop on val PR-AUC → sweep 19 thresholds in [0.05, 0.95], pick best val F1 → isotonic-calibrate when val ECE > 0.05 → evaluate once on test.

🔀 Scenario A vs B — what changes

Same training loop. The only difference is which feature columns each model is allowed to read.

Scenario A
pre-departure · 37 features
"It's 2 hours before this train leaves. Will this stop be disrupted?"
→ station info, weather forecast, time of day, lag rates, route plan
Scenario B
inflight · 40 features = A + 3
"Train has already passed some stops. Will the next one be disrupted?"
→ A's columns + prev_stop_actual_delay, cum_actual_delay_so_far, max_actual_delay_so_far

Those 3 inflight columns are why B crushes A (PR-AUC ~0.52 → 0.94). The lag-feature ablation in §② SHAP confirms the entire uplift collapses to ~0.35 when both lag and inflight columns are removed.

🔍

TreeSHAP attributes the win

Why does XGBoost reach PR-AUC 0.939 on inflight data? TreeSHAP (the canonical exact-attribution method for tree ensembles) was run on a 271 k stratified subsample of the 2.71 M-row test set. The top driver in scenario A is train_station_lag7_rate (mean |SHAP| 1.061); in scenario B it collapses to a single feature: prev_stop_actual_delay (mean |SHAP| 2.464) — almost 4× the second strongest.

Bridge query template (Cypher)

Canonical Cypher form (portable to Kuzu / Neo4j / Sparksee 6+). The shipped build implements the same query against Sparksee 5.2.3 via the native findEdge / explode / neighbors calls — see stop_level/build_kg.py::run_bridge_demo.

MATCH (svc:TrainService {service_id: $sid})-[stop:STOPS_AT]->(st:Station {station_id: $stid})
OPTIONAL MATCH (f:FaultEvent)-[:REPORTED_AT]->(st)
  WHERE f.date >= date($d) - INTERVAL('14 days') AND f.date <= date($d)
OPTIONAL MATCH (st)-[adj:ADJACENT_TO]->(nbr:Station)
RETURN st.station_id, st.country, st.avg_historical_delay, st.degree,
       stop.delay_minutes, stop.weather_severity,
       count(DISTINCT f) AS recent_faults_14d,
       count(DISTINCT nbr) AS n_neighbours,
       collect(DISTINCT nbr.station_id) AS all_neighbours
