\section{Knowledge graph integration}
\label{sec:kg}

\subsection{Why a graph at all?}

The four-model benchmark and the SHAP report deliver per-row probabilities and per-row attributions. Both are useful but neither answers the question an operations analyst will ask next: \emph{why is this stop on the high-risk list?} Answering it requires the surrounding context -- the station's reliability history, recent fault reports, the immediate neighbours on the network. That context is graph-shaped: services connect to stations, stations connect to stations, fault events connect to stations. We therefore promote the Phase~1/2 outputs to a queryable graph database and define a single bridge query that takes a $(\texttt{service\_id}, \texttt{station\_id}, \texttt{date})$ triple from the SHAP report and returns the surrounding spatial-temporal neighbourhood.

\subsection{Schema and backend}

The chosen backend is Sparksee~5.2.3~\cite{sparksee2024,martinez2017dex}, sourced from Maven Central as \texttt{com.sparsity:sparkseejava:5.2.3}. The published jar already bundles the Linux x86\_64 native libraries (\texttt{libsparksee.so}, \texttt{libsparkseejavawrap.so}, \texttt{libstlport.so}); we drive the JVM-side API from Python via JPype1. The repository ships a one-shell-command installer (\texttt{scripts/install\_sparksee.sh}) that downloads the jar and a portable Eclipse Temurin~17 JDK into a project-local \texttt{.tools/} directory, so neither a Sparksee account nor a system-level Java install is required.

The schema uses three node types and three edge types. \Cref{lst:kg-schema} expresses it as Cypher DDL, the canonical portable description; the actual Sparksee build creates the same structure through the equivalent native API calls (\texttt{Graph.newNodeType}, \texttt{Graph.newEdgeType}, \texttt{Graph.newAttribute}).

\begin{figure}[htbp]
\begin{lstlisting}[language=Cypher]
CREATE NODE TABLE Station(
    station_id            STRING,
    country               STRING,
    lat                   DOUBLE,
    lon                   DOUBLE,
    avg_historical_delay  DOUBLE,
    degree                INT64,
    PRIMARY KEY (station_id));
CREATE NODE TABLE TrainService(
    service_id        STRING, country STRING,
    train_class_code  INT64,  date DATE,
    is_disrupted      INT64,
    PRIMARY KEY (service_id));
CREATE NODE TABLE FaultEvent(
    fault_id     STRING, date DATE, description STRING,
    PRIMARY KEY (fault_id));
CREATE REL TABLE STOPS_AT(
    FROM TrainService TO Station,
    delay_minutes      DOUBLE, weather_severity   INT64,
    temperature DOUBLE, wind_speed DOUBLE,
    precipitation DOUBLE, snow_depth DOUBLE);
CREATE REL TABLE ADJACENT_TO(FROM Station TO Station, distance_km DOUBLE);
CREATE REL TABLE REPORTED_AT(FROM FaultEvent TO Station);
\end{lstlisting}
\caption{Knowledge-graph schema in Cypher DDL (the portable description). Three node types and three edge types. The Sparksee~5.2.3 backend creates the same structure through the equivalent native-API calls; only the driver call sites differ.}
\label{lst:kg-schema}
\end{figure}

\subsection{Build statistics and the evaluation-mode cap}

The Maven Central jar runs Sparksee in \emph{personal evaluation} mode unless a licence string is provided in \texttt{sparksee.cfg}. Evaluation mode caps each edge type at one million edges. The full \texttt{STOPS\_AT} relation contains \num{16586834} edges, well above that cap, so the build script automatically falls back to a representative \emph{hub subgraph} centred on the SHAP demo station \texttt{FI\_HKH}: every service that visits the hub or any of its 1-hop adjacent stations, together with the corresponding \texttt{STOPS\_AT}, \texttt{ADJACENT\_TO} and \texttt{REPORTED\_AT} edges. Holders of an academic or commercial Sparksee licence can drop their licence string into \texttt{sparksee.cfg} and re-run with the same code path to load the full \num{16.59}\,M-edge graph. \Cref{tab:kg-build} reports build wall-clock for the eval-mode hub subgraph on a Tesla~T4 / 4-core CPU box.

\subsection{Bridge query: closing the loop from SHAP to context}

The point of the graph is to translate a black-box probability into a queryable spatial-temporal neighbourhood. After the SHAP report flags a high-risk stop, the analyst plugs $(\texttt{service\_id}, \texttt{station\_id}, \texttt{date})$ into the bridge query. \Cref{lst:kg-bridge} shows the canonical Cypher form (portable to Kuzu, Neo4j, or Sparksee~6+ OpenCypher); \texttt{stop\_level/build\_kg.py::run\_bridge\_demo} implements an exactly equivalent native-API translation against Sparksee~5.2.3 using \texttt{Graph.findEdge}, \texttt{Graph.explode} and \texttt{Graph.neighbors}.

\begin{figure}[htbp]
\begin{lstlisting}[language=Cypher]
MATCH (svc:TrainService {service_id: $sid})-[stop:STOPS_AT]->(st:Station {station_id: $stid})
OPTIONAL MATCH (f:FaultEvent)-[:REPORTED_AT]->(st)
  WHERE f.date >= date($d) - INTERVAL('14 days') AND f.date <= date($d)
OPTIONAL MATCH (st)-[adj:ADJACENT_TO]->(nbr:Station)
RETURN
  st.station_id          AS station,
  st.country             AS country,
  st.avg_historical_delay AS station_avg_delay,
  st.degree              AS degree,
  stop.delay_minutes     AS this_stop_delay,
  stop.weather_severity  AS weather_severity,
  count(DISTINCT f)      AS recent_faults_14d,
  count(DISTINCT nbr)    AS n_neighbours,
  collect(DISTINCT nbr.station_id) AS all_neighbours
\end{lstlisting}
\caption{The bridge query in canonical Cypher form. It takes a SHAP-flagged $(\texttt{service\_id}, \texttt{station\_id}, \texttt{date})$ triple and returns the surrounding spatial-temporal context: this stop's actual delay and weather, recent fault events at this station, and the 1-hop adjacent stations.}
\label{lst:kg-bridge}
\end{figure}

\paragraph{Live demo.} For the highest-confidence true-positive disruption from the scenario-B XGBoost model -- service \texttt{FI\_28\_2024-06-30} stopping at \texttt{FI\_HKH} on \texttt{2024-06-30}, predicted with $p=1.000$ -- the native-API bridge query returns the result in \cref{lst:kg-result} in \SI{7.7}{ms}. The same query expressed as Cypher and executed by Kuzu's planner takes \SI{52}{ms}; Sparksee's direct \texttt{findEdge} call avoids the explode-and-filter pattern Cypher's planner falls back to.

\subsection{Reproducibility one-liner}

\begin{lstlisting}[language=bash]
# 1. Install Sparksee 5.2.3 (Maven Central jar) + portable Temurin JDK 17.
#    Idempotent — re-running is a no-op if both are already present.
source scripts/install_sparksee.sh

# 2. Build the KG and run the bridge demo. Drops any prior DB.
python stop_level/build_kg.py --rebuild
\end{lstlisting}

\paragraph{Licence tier.} The repository ships \texttt{sparksee.cfg.example} with cache and storage tuning but no licence string. Holders of an academic or commercial Sparksee licence can copy it to \texttt{sparksee.cfg} and add their \texttt{sparksee.license = ...} line; the build then loads the full \num{16586834}-edge graph through the same code path. Without a licence, the script auto-degrades to the FI\_HKH hub subgraph reported in \cref{tab:kg-build}, which is still enough to demonstrate the bridge query end to end.
